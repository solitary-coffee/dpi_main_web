# XML Embedプレビューと稼働モード拡張（Phase 1 / ドラフト）

この変更だけでは新モードを有効化できない。特に緊急停止の実装完了・本番適用を意味しない。
`RUNTIME_INTEGRATION_COMPLETE=False` を手動で変更してはならない。

## 実装したもの

- XML管理配信用の共通レンダラー。プレビューと送信で同一のDiscord JSONを生成する。
- 本文は省略せず分割する。40メッセージを超えるXMLは送信を拒否する。
- XML・配信枠・経路・レンダラーバージョンのダイジェスト一致を送信時にも検証する。
- 変更中に古いプレビュー応答が返っても送信ボタンを有効にしない。
- `title`を文字列ではなくDiscordメッセージJSON、`data`をXML文字列ではなく経路キーに修正。
- 日本語確認文字列の`hmac.compare_digest`例外をUTF-8バイト比較で修正。
- モード選択肢、5ノードの設定/実測/反映時刻、手動モードの個別設定欄。
- 配信側の対応が未完了の新モードをUIとAPIの両方で無効化。

プレビューは**このXML管理配信で実際に送る形式**。自動配信の種別別レンダラーの移植ではない。
Discordのクライアント依存のMarkdown表示やレイアウトまでピクセル単位で再現するものではない。
送信JSONを開いて内容を確認できる。訓練・試験XMLも状態を表示するので、本番枠へ誤送信しないこと。

### 確定した実装上の注意

- `mode_runtime.delivery_wait` はHOMEレコードとMODEレコードを読み、`decide`で再判定する。
  管理画面が固定モードを書くだけでは、自宅が正常なときに指定が上書きされ得る。
- 現行`wait_seconds("EMERGENCY", ...)`は未知のモード扱いで**3秒**になる。
  2台それぞれで送信やAWSアクセスを含まない純粋関数テストを6件実行し確認した。
- EEWと気象は別の送信入口を使用する。EEWは`backup_receiver._process`、
  気象は`_backup_guard_v51_claim`から待機処理・配信権取得へ進む。
- 停止判定は待機時間計算だけでなく、待機終了後・配信権取得前・実際の送信前にも必要。
  `HOME_SEEN`/`BACKUP_CLAIMED`の抑止は維持する。
- 現行の例外時「3秒待機で配信継続」というフォールバックを、緊急停止確認失敗時には使えない。
- この検証は既存動作の確認であり、新しい6モードの統合試験成功を意味しない。

## モード契約

| モード | 自宅 | EC2 |
|---|---|---|
| 自動監視 | 既存動作 | 既存の死活判定・復旧判定 |
| 通常 | 即時 | 基本2台は3秒待機、残り2台は停止配置 |
| スタンバイ | 即時 | 既存BACKUP_STANDBY：基本2台即時、補助2台3秒待機 |
| バックアップ | 即時（稼働している場合） | 既存BACKUP：全台待機なし |
| 手動 | 即時/待機/配信停止 | 4台を個別に即時/待機/配信停止 |
| 緊急 | 即時 | 自宅の生死を問わず待機なし。起動に必要な時間は別 |
| 緊急停止 | 配信停止 | 配信停止。制御エージェントは動かして適用確認を返す |

どのモードでも二重配信防止は維持する。送信済みのDiscord通知は緊急停止で撤回できない。

## 適用上の注意

ドラフト段階なので新モード目的で本番へ適用しないこと。
XML部分を先行適用する場合も、AWS APIに`xml_delivery.py`と`operating_modes.py`を含めてSAMでビルドする。
`lambda_function.py`だけのZIP更新は不可。AWSのAPIを先に更新し、その後サイトを更新する。
旧フロントからのXML配信はダイジェスト不足で拒否するため、必ず新画面で再プレビューする。
Cloudflareのログインやデプロイはユーザー側で行う。既存のブラウザー適用手順を参照する。
