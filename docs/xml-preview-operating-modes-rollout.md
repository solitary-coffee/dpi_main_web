# XML Embedプレビューと稼働モード拡張（ランタイム統合中 / ドラフト）

この変更だけでは新モードを有効化できない。特に緊急停止の実装完了・本番適用を意味しない。
`RUNTIME_INTEGRATION_COMPLETE=False` を手動で変更してはならない。

## 実装したもの

- XML管理配信用の共通レンダラー。プレビューと送信で同一のDiscord JSONを生成する。
- 本文は省略せず分割する。40メッセージを超えるXMLは送信を拒否する。
- XML・配信枠・経路・レンダラーバージョンのダイジェスト一致を送信時にも検証する。
- 変更中に古いプレビュー応答が返っても送信ボタンを有効にしない。
- `title`を文字列ではなくDiscordメッセージJSON、`data`をXML文字列ではなく経路キーに修正。
- 日本語確認文字列の`hmac.compare_digest`例外をUTF-8バイト比較で修正。
- モード選択肢、5ノードの設定/実測/反映時刻、手動モードの個別設定欄。
- 配信側の対応が未完了の新モードをUIとAPIの両方で無効化。
- 管理操作をDynamoDBの条件付き更新で直列化。副作用より先に変更番号を確保する。
- 自動監視へ戻しても変更番号と停止期間の破棄境界を保持する。
- 部分失敗を記録して画面に表示。変更要求の受付を反映完了と表示しない。
- 手動モードのフォームを保存済みノード設定で初期化する。
- `delivery_gate.py` に停止・待機・解除後の旧電文拒否を共通化（送信経路への接続は未完了）。
- `mode_hooks.py` と `scripts/prepare-mode-runtime.py` に実行環境への接続処理を追加。
  本番から読み取ったコードのコピー9種類で更新と構文確認に成功。本番ファイルは未更新。

### 実行環境の更新準備

更新スクリプトは入力スナップショットを上書きせず、別ファイルに更新版を生成する。
挿入箇所が1件に定まらない場合は失敗させる。本番ソースや秘密情報はこの公開リポジトリへ含めない。

`DPI_MODE_ENABLED=1` で接続処理を有効化する設計だが、**全体未完了のため現在は設定しない**。
実行モジュールの検索パスへ `mode_hooks.py` / `delivery_gate.py` / `operating_modes.py` が必要。
AWS/EC2は `DPI_MODE_NODE`、`DPI_MODE_REGION`、`DPI_MODE_STATE_TABLE` を明示設定し、
状態レコードのGetItem権限が必要。自宅は `DPI_MODE_NODE=home` と `DPI_MODE_FILE` が必要。
自宅は既存の認証済みheartbeat応答でモードを受け取り、同じリビジョンの矛盾や古い応答を拒否する。
新しい正常応答がなくなればファイルの鮮度45秒とゲートキャッシュの有効期限で送信を止める設計。

受付・worker・自宅HTTP・EEW受信・EEW HTTPの5つについて、更新後の実関数を読み込んだ
無通信テストで緊急停止時に配信権取得/HTTP送信へ進まないことを確認した。
これは本番実行や全経路検証ではない。スナップショットのないCIでは5件をskipとして明示する。
実行時は `DPI_PREPARED_RUNTIME_DIR` に生成先を指定して `tests/test_prepared_runtime.py` を実行する。

### 2026-10-20 追加実装の検証範囲

`tests/test_delivery_gate.py` の14件はネットワークも実配信も使わない。
待機中の停止、緊急モードへの変更による待機短縮、再試行直前の停止、
旧電文・時刻欠落・未来時刻の拒否、制御読み取り障害時の有効期限、
古いリビジョンや同番号の矛盾した応答の拒否、1,000送信先に対する読み取り共有、
手動での自宅待機とEC2停止、管理操作の競合・部分失敗を検証する。
既存XML/モードの8件と合わせてPythonテスト22件。

共通ゲートの既定値は更新間隔5秒・有効期限10秒。これはプロセス単位のキャッシュであり、
1送信先につきDynamoDBを読む設計ではない。待機中は100msごとにキャッシュを確認する。
この値は本番の停止反映保証ではない。自宅への設定伝達・リージョン複製・全経路接続後に
実測値を表示する必要がある。ゲートのロードだけでは `verified=True` を返さない。

管理APIの操作リースは180秒。現行SAMのLambda Timeout=120秒より長く、
タイムアウトした操作の後に再操作できる。LambdaのTimeoutを延長する際はリースも見直す。
APIは単一の管理リージョンから書き込む。東京・大阪の状態テーブルは複製されているが、
別リージョンから同時に条件付き更新してグローバル排他が成立すると想定してはならない。

プレビューは**このXML管理配信で実際に送る形式**。自動配信の種別別レンダラーの移植ではない。
Discordのクライアント依存のMarkdown表示やレイアウトまでピクセル単位で再現するものではない。
送信JSONを開いて内容を確認できる。訓練・試験XMLも状態を表示するので、本番枠へ誤送信しないこと。

### 確定した実装上の注意

- `mode_runtime.delivery_wait` はHOMEレコードとMODEレコードを読み、`decide`で再判定する。
  管理画面が固定モードを書くだけでは、自宅が正常なときに指定が上書きされ得る。
- 現行`wait_seconds("EMERGENCY", ...)`は未知のモード扱いで**3秒**になる。
  2台それぞれで送信やAWSアクセスを含まない純粋関数テストを6件実行し確認した。
- EEWと気象は別の送信入口を使用する。EEWは`backup_receiver._process`、
  気象は`_backup_guard_v51_claim`から待機処理・配信権取得へ進む。
- 停止判定は待機時間計算だけでなく、待機終了後・配信権取得前・実際の送信前にも必要。
  `HOME_SEEN`/`BACKUP_CLAIMED`の抑止は維持する。
- 現行の例外時「3秒待機で配信継続」というフォールバックを、緊急停止確認失敗時には使えない。
- この検証は既存動作の確認であり、新しい6モードの統合試験成功を意味しない。

## モード契約

| モード | 自宅 | EC2 |
|---|---|---|
| 自動監視 | 既存動作 | 既存の死活判定・復旧判定 |
| 通常 | 即時 | 基本2台は3秒待機、残り2台は停止配置 |
| スタンバイ | 即時 | 既存BACKUP_STANDBY：基本2台即時、補助2台3秒待機 |
| バックアップ | 即時（稼働している場合） | 既存BACKUP：全台待機なし |
| 手動 | 即時/待機/配信停止 | 4台を個別に即時/待機/配信停止 |
| 緊急 | 即時 | 自宅の生死を問わず待機なし。起動に必要な時間は別 |
| 緊急停止 | 配信停止 | 配信停止。制御エージェントは動かして適用確認を返す |

どのモードでも二重配信防止は維持する。送信済みのDiscord通知は緊急停止で撤回できない。

## 適用上の注意

ドラフト段階なので新モード目的で本番へ適用しないこと。
XML部分を先行適用する場合も、AWS APIの同ディレクトリ内Pythonモジュールをすべて含めてSAMでビルドする。
`lambda_function.py`だけのZIP更新は不可。AWSのAPIを先に更新し、その後サイトを更新する。
旧フロントからのXML配信はダイジェスト不足で拒否するため、必ず新画面で再プレビューする。
Cloudflareのログインやデプロイはユーザー側で行う。既存のブラウザー適用手順を参照する。
